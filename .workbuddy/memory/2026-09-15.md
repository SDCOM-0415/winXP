### 校验脚本的两个坑（都已修）
1. **展开语法误报**：`...target` 前面是点号，会被
   `(?<![\w.$])name(?![\w$])` 的边界正则漏算，导致"未使用声明"误报。
   修法：计数前先把源码里的 `...` 替换成空格再匹配。
2. **eslint-disable 的反噬**：用 `[]` 空依赖 + `eslint-disable-next-line

## 图片查看器 + 图片资源机制（**未提交，待用户指示**）

### 关键发现：图片约定项目里本来就有
- VFS 的**图片节点把资源路径存在 `contents` 字符串上**，例如
  `"contents": "res/pictures/bluehills.jpg"`
- `C:\Documents and Settings\All Users\Shared Pictures\Sample Pictures` 下
  本来就有 XP 的四张示例图（Blue Hills / Sunset / Water Lilies / Winter）**条目**
- 但这些 `res/pictures/*.jpg` 是**悬空引用**：项目和爬取副本里都没有这些文件
- E 盘（Goodies CD）那 4 张 Microsoft 怀旧图在参考站里是 `microsoft_nostalgic.zip` 的内容，
  爬取时被解到了 `vfs/E/microsoft_nostalgic/`

### 做了什么
1. 新增 `src/assets/pictures/microsoft_nostalgic/`（4 张 jpg，共 840K）
2. `vfs/index.js` 新增图片资源解析，沿用项目已有的 `require.context` 约定：
   - `pictureMap`：以 `assets/pictures` 下的相对路径为键（递归）
   - `pictureByName`：按文件名兜底索引
   - `resolvePicture(contents)`：支持 `data:` / `http(s):` / 项目内相对路径三种写法，
     **解析不到返回 null，由调用方显示占位提示，不伪造图片**
   - `isImageName(name)`：按扩展名判断
   - `listPictures()`：列出全部图片（备用）
3. `drive_e_goodies.json` 新增 `microsoft_nostalgic` 目录，4 个文件节点的
   `contents` 写**精确相对路径**（如 `microsoft_nostalgic/xxx.jpg`），
   与 `require.context` 的键一一对应，不依赖兜底匹配
4. 新增 `apps/ImageViewer/`：上一张 / 下一张（同目录图片序列）、
   放大 / 缩小 / 实际大小 / 最佳适应 / 顺逆时针旋转、状态栏
5. 文件关联：`MyComputer.openEntry` 与 `WinXP.onDoubleClickIcon` 都加了图片分支

### 两个踩到的坑
1. **图片必须先于 `isEditableText` 判断**：图片节点的 `contents` 是字符串，
   `isEditableText` 会返回 true，不先分流的话图片会被记事本当文本打开。
2. **「实际大小」不能用 CSS 的 max-width 拟合**：初版把 `max-width/max-height:100%`
   与 `transform: scale()` 叠加，导致 100% 并不是真实像素。
   改成：最佳适应交给 CSS 约束（scale 固定 1），其余模式去掉约束、
   按 `zoom/100` 缩放，这样 100% 才是真正的实际大小。
   （顺带丢掉了原本需要的舞台尺寸测量与图片自然尺寸记录）
3. 又差点写 `eslint-disable react-hooks/exhaustive-deps`，已改用 ref 守卫。
4. **prettier 会按默认 tabWidth=2 重排 JSON**，把 `drive_e_goodies.json`
   从 4 空格改成 2 空格，产生 172 行无谓 diff、且与兄弟文件 `drive_c_system.json`
   （4 空格）不一致。**JSON 不要交给 prettier 处理**，用 `JSON.stringify(d,null,4)` 写回即可，
   diff 降回 27 行。注意 CI 的 prettier 规则只作用于 JS，不管 JSON，所以无风险。

### 接线方式（关键决定：放 public/，不进 bundle）

- CRA 会把 `public/` 原样拷进构建产物，所以这 9.4M **只在用户真正打开弹球时才请求**，
  不进主 JS bundle、不影响首屏。这是相比"import 到 src"最大的收益。
- 已删除先前放在 `src/assets/pinball/` 的那两个媒体文件，避免 2.8M 双份

### 那份 JS 的内部构成（已确认）
1. `var WASM_FILE = "data:application/wasm;base64,..."` → 6.05M base64，解码后 **4.33MB WASM**
2. `var DATA_FILE = "data:application/octet-stream;base64,UklGR..."` → `RIFF/WAVE` 头，
   即**游戏音频也内嵌**
3. Emscripten 加载器，末尾调 `run()` **自动执行**
→ 完全自包含，`PINBALL.DAT` 由 `--preload-file` 打入，运行时不需再下载

### 宿主页面的实现要点
- 用 **iframe** 承载，而不是直接挂 canvas。原因：它是一份自带文档与输入处理的
  完整 Emscripten 应用，隔离在独立文档里才不会和主应用的全局键盘处理
  （屏保空闲计时等）互相干扰
- `window.Module` 必须在 `3DPinballSpaceCadet.js` **之前**定义（Emscripten 加载时读取）
- **键盘转发**：在 document 的**捕获阶段**拦下游戏按键，
  `preventDefault + stopPropagation` 后**定向重新派发给 canvas**，
  这样无论焦点在哪都只送达一次，也不会误吞浏览器快捷键（跳过了带修饰键的）
- 转发键位：`z` `Z` `/` `?` 空格 回车 方向键 `F2` `F3` `F4` `Esc`
- `bg.mp3` 是**原版 MIDI 背景音乐的替代品**（WASM 播不了 MIDI）。
  浏览器禁止无交互自动播放，所以改成**首次 mousedown/keydown 时启动**，
  并在右上角放了音乐开关
- splash 在 `Module.onRuntimeInitialized` 时淡出，另有 15s 兜底定时器

### 没有加菜单栏（重要）
3D 弹球是 Win32 程序，**它的菜单栏（游戏/选项/帮助）由它自己在 canvas 上绘制**。
所以本应用只提供承载 iframe 的窗口，**不叠加自己的 dropDownData**，
否则会出现两条菜单栏。也因此没有建 `dropDownData.js`。

## 窗口客户区对齐（**未提交**）

### 发现：`.app__content` 完全没有边框与内阴影
基准的 `appcontents` 规格（`css/luna/modules.css`）给每个窗口的客户区都加了：

```css
margin: 0 2px 2px;
background-color: var(--contentColor);   /* #fff */
border: 1px solid;
border-color: #777792 #66667e #66667e #66667e;
box-shadow: -1px 0 0 #a8a9bb, 1px 0 0 #a8a9bb, 0 1px 0 #a8a9bb;
letter-spacing: -.2px;
box-sizing: border-box;
```

而我们的 `.app__content` 只有 `flex/position/margin-top/height`，**一条视觉规则都没有**。

### 基准对「对话框」用的是另一套值
```css
app.dialogbox appcontents {
    box-shadow: -1px 0 0 #fbfcfd, 1px 0 0 #fbfcfd, 0 1px 0 #fbfcfd;
    margin: 0 1px 1px;
    background-color: var(--mainColor);   /* #ece9d8 */
}
```
本项目里 **`header.invisible` 正好对应对话框**（ErrorBox / AboutWindows / Winamp），
所以用 styled-components 的 `header` prop 分两套取值。

### 本次只加了视觉部分，**故意没加那 2px 外边距**
窗口本身已有 `padding: 3px`，客户区距边缘本来就是 3px；
再加 2px 只是变成 5px，视觉差异很小，而加外边距会改变**每一个窗口**的尺寸计算、
有布局回归风险。所以只加 `border + box-shadow + background + letter-spacing + box-sizing`，
**不动定位**。

### 我们的结构与差异
`MyComputer` 的三段式结构（`.com__toolbar` / `.com__function_bar` / `.com__address_bar`）
**本来就和基准的三行对应**，但用的是作者手挑的颜色：
`rgba(255,255,255,.7)` / `rgba(0,0,0,.1)`，并且**完全没有那条浅色背景渐变**。

### 本轮改动
1. 三个导航行都加上 `background: linear-gradient(to right, #f4f4ee, #e0e2eb)`
   （渐变是横向的，所以逐行加与加在父容器上视觉一致，无需改 DOM）
2. 分隔线统一为**上白下灰**：`border-top: 1px solid #fff` +
   `border-bottom: 1px solid #d8d2bd`
3. 右上角标志由 `windowsIcons/windows.png` 换成基准指定的 `ui/browserflag.png`
   （两者都是 39×22，但后者带透明通道、质量更好），边框改为 `#d8d2bd`
4. 移除了地址栏上基准没有的 `box-shadow: inset 0 -2px 3px -1px #b0b0b0`
5. `.com__options` 原本重复画了一条内部分隔线，去掉，交给行的 border

**确认过不会出现双线**：`.com__content` 是 `border: 1px solid rgba(0,0,0,.4)`
配 `border-top-width: 0`，地址栏的下边线不会与它叠成两条。

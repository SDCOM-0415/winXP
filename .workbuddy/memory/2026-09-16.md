## 1. 修复：右键子菜单在屏幕右侧溢出（靠边右键时「新建」看不到）

### 用户反馈
"桌面和我的电脑的新建点击后都不显示"，且确认是在本地 dev server 上测试。

### 根因
主菜单做了边界收敛（`Math.min(clientX, innerWidth - mw - 2)`），
**但子菜单是 `contextmenu > ul ul { left: 100% }` 死板向右展开，没有任何溢出处理**。

实测（视口 1280，在 x=1150 处右键）：

| | left | right | 溢出 |
|---|---|---|---|
| 主菜单 | 1118 | 1278 | 否（已收敛）|
| **子菜单**（排列图标 / 新建） | 1275 | **1435** | **是，超出右边界 155px** |

子菜单整个渲染到视口外 → 用户看不到、点不到 → 表现为"新建不显示"。

**我为什么前两次测不出来**：一直点在屏幕中间（x≈420~500），子菜单有空间向右展开。

### 修复
1. `WinXP/index.js` 全局右键处理器：克隆菜单并定位后，遍历 `li.submenuholder`，
   **临时 `display:block + visibility:hidden` 量出子菜单宽度**
   （平时是 `display:none` 量不到宽度），若
   `holder.getBoundingClientRect().right + 子菜单宽 > window.innerWidth`
   则加上 `submenu-left` 类
2. `index.css` 新增：
   ```css
   contextmenu > ul li.submenuholder.submenu-left > ul {
     left: auto;
     right: 100%;
   }
   ```

### 验证（两个方向都测）
| 右键位置 | flipLeft | 子菜单位置 | 结果 |
|---|---|---|---|
| 靠右 x=1150 | `true` | left 961 → right 1121 | 向左展开，不溢出 ✅ |
| 靠左 x=200 | `false` | left 357 → right 517 | 仍向右展开，行为不变 ✅ |

### 未做但已知的同类问题
子菜单的 `top: -3px` **也没做垂直溢出处理**——在屏幕底部右键时子菜单可能往下方超出。
已告知用户，待其确认是否遇到。

## 6. 🎯 真正的根因：`onMouseDownDesktop` 无条件删除右键菜单（已修复并真实鼠标验证）

### 用户反馈
"依旧没有任何作用，而且这不是右键菜单的问题，是完全没有任何新建效果生效"

### 根因（用 `Element.prototype.remove` 打桩抓出的调用栈）
```
Element.remove ← HTMLDocument.dismiss (main.js:20054)
              ← onMouseDownDesktop (main.js:20159)  ← React callCallback
```

`WinXP/index.js` 里：
```js
function onMouseDownDesktop(e) {
  document.querySelector('contextmenu.visible')?.remove();   // ← 罪魁祸首
  ...
}
```
右键菜单是 `appendChild` 到该容器**内部**的，所以**点在菜单项上的 mousedown 会冒泡到这里**，
菜单被无条件删掉。事件序列实测：

```
mousedown target=LI  li=文件夹  inMenu=true    ← 按在菜单项上
mouseup   target=DIV inMenu=false              ← 抬起时菜单已经没了
```

**菜单在 mousedown 到 mouseup 之间消失 → 浏览器判定"不是一次完整点击"→
`click` 事件永不触发 → 所有菜单项的处理器都不执行。**

这解释了用户最初的"所有东西都只实现了按钮效果、实际全部失败"：
**任何右键菜单项在真实鼠标下都点不动**。

### 为什么我之前所有测试都"通过"了
我一直用 JS 直接调 `el.click()`。**程序化 `.click()` 不会触发 mousedown**，
所以绕过了这个 bug。这是本次排查最大的方法错误。

### 修复
```js
const openMenu = document.querySelector('contextmenu.visible');
if (openMenu && openMenu.contains(e.target)) return;   // 点在菜单内，交给菜单自己处理
openMenu?.remove();
```
（全库只有两处删除菜单：另一处在 `contextmenu` 事件里，作用是开新菜单前关旧的，逻辑正确。）

### 验证（**全程真实鼠标输入** `agent-browser mouse move/down/up`）
| 场景 | 结果 |
|---|---|
| 桌面：真实右键 → 悬停新建 → 真实点文件夹 | Desktop 条目 4 → **5**，桌面出现「新建文件夹」✅ |
| 我的电脑：进 C 盘 → 真实右键 → 悬停 → 真实点文件夹 | 列表 4 → **5**，「新建文件夹」出现在首行 ✅ |

### ⚠️ 方法论（必须记住）
**验证交互功能必须用真实输入**，不能用程序化 `.click()` / `dispatchEvent`。
`agent-browser` 的真实输入方式：
```bash
agent-browser mouse move <x> <y>
agent-browser mouse down left      # 或 right
agent-browser mouse up left
```
定位元素坐标用 `getBoundingClientRect()` 算出中心点再 `mouse move` 过去。
**这次就是靠真实输入才复现出用户的问题**——此前三轮"我这边正常"全是假阳性。

### 另一个可复用的排查技巧
给 `Element.prototype.remove` 和 `Node.prototype.removeChild` 打桩，
在元素被删时记录 `new Error().stack`，能**直接点名是哪段代码删的**。
本次正是靠这个从"菜单莫名其妙消失"一步定位到 `onMouseDownDesktop`。

## 8. 新建的三个问题：网格布局（已修）＋ 立即重命名（回退，待重做）

### 用户反馈
"创建文件默认修改文件名没有实现，而且在修改完成名称后会自动往下一格，
而且文件创建是在右键区域而不是默认位置新建"

### 实测确认的三个问题
1. **新图标排到屏幕外**：位置分配是「无限往首列下方追加」（`y: index * 75`），
   7 个内置图标之后新图标落在 y=610、685、985…全部超出 633px 视口。
   用户看到的就是"什么都没出现"
2. **创建后没有进入重命名态**：确认未实现（这轮做了又回退，见下）
3. **重命名后图标跳位**：重命名改变图标 id（`vfs:旧名 → vfs:新名`），
   位置表里没有新 id，被当成新图标排到下一个空位

### 已修复（真实鼠标验证通过）
1. **网格布局 + 换列**：`getInitialPositions` 与"补位"effect 都改为
   80×75 的网格，`rows = floor((innerHeight - 40) / 75)`，一列满则换列。
   实测：16 个图标（含新建的 (8).txt）**全部可见，零溢出**
2. **重命名后保持原位**：给 `Icons` 增加 `migratePosition(oldId, newId)`
   的命令式方法，`onRenameDesktopIcon` 在派发 `VFS_RENAME` 后调用
   （图标 id 格式是 `vfs:${name}`）

### ⚠️ 回退：「新建后立即重命名」引发了更糟的回归
第一版实现：创建的 dispatch 后**立刻** `setPendingRename(...)` 广播事件。
结果实测发现 **`VFS_CREATE_FILE` 之后文件没有真正落进 VFS**
（插桩显示：创建分支执行了、`setPendingRename` 生效了、effect 也跑了、
但 VFS 里没有新文件，且事件从未广播）。

由于无法在剩余时间内定位这个回归，**已把该部分整体回退**，
回退后创建功能恢复正常（真实鼠标验证 (7)(8) 都能创建）。
**结论：这个功能需要重新设计，不能在同一个 click 回调里
"dispatch 创建 + 依赖同步后的图标列表"两件事混在一起做。**
可能的方向：让 Icons 组件直接以 prop 接收"待重命名目标"，
在它自己的 render 里（icons 一定是新的）匹配；或者由 reducer 一次性
完成"创建 + 标记待重命名"。
